###################
5.1.3 release notes
###################

*September 16, 2026*

Welcome to django CMS 5.1.3!

These release notes cover what has changed since django CMS 5.1.2. This patch
release fixes broken access control in the page tree, the add-page form and the
page wizard, a stored XSS in the page delete confirmation, and it repairs
migration ``cms.0045`` on PostgreSQL. Read the security fixes and their
backward-incompatible effects before updating an existing project.

If you are upgrading from django CMS 5.0.x or earlier, read the
:ref:`5.1.0 release notes <upgrade-to-5.1.0>` first — they cover the backward
incompatible changes, deprecations, and removals of the 5.1 series.

*******************************
Django and Python compatibility
*******************************

django CMS 5.1 supports **Django 5.2, 6.0, and 6.1**. Django 4.2, 5.0, and
5.1 are no longer supported because those series no longer receive upstream
maintenance. We highly recommend and only support the latest release of each
supported series.

It supports **Python 3.10, 3.11, 3.12, 3.13, and 3.14**.

***********************
How to upgrade to 5.1.3
***********************

Before upgrading, back up your database and review the
:ref:`backward-incompatible changes <upgrade-5.1.3-backward-incompatible>`
below.

Upgrade django CMS::

    python -m pip install --upgrade "django-cms==5.1.3"

Then collect static files and run the django CMS checks::

    python manage.py collectstatic --noinput
    python manage.py cms check

This release adds no new migrations. It repairs
``cms.0045_pageurl_site_unique_path``, which failed on PostgreSQL for databases
containing duplicate page paths with *cannot ALTER TABLE "cms_pageurl" because
it has pending trigger events*. If that migration failed for you, run it again
after upgrading::

    python manage.py migrate

Databases that already applied the migration successfully are unaffected.

*******************
What's new in 5.1.3
*******************

Security fixes
==============

This release fixes four advisories. All of them require an authenticated
staff account; none is exploitable anonymously. We recommend that all users
upgrade as soon as possible.

Page-tree copy, duplicate and move disclosed view-restricted pages
------------------------------------------------------------------

This release fixes broken access control in the page tree's *Copy*, *Duplicate*
and *Move* operations. All three require ``CMS_PERMISSION = True`` and at least
one per-page view restriction: an installation that does not use the permission
system has nothing to disclose, because ``Page.has_view_restrictions()`` is
always ``False`` there. Each of them needs a staff session that may add pages;
none is exploitable anonymously, but the content they expose is readable
anonymously afterwards.

`GHSA-976q-w6ch-6w82 <https://github.com/django-cms/django-cms/security/advisories/GHSA-976q-w6ch-6w82>`_
covers all three, which share a root cause, their prerequisites and their fix:

* *Copy* authorized only the root of the subtree it was asked to copy, while
  every descendant below it was copied and recreated without its view
  restrictions. A delegated editor who could view one public page therefore
  obtained a publicly readable copy of every view-restricted page below it.
  Selecting *Copy permissions* did not help: the flag was passed to the
  descendants but not to the copied root, so the root lost its own permission
  records as well. Copying now authorizes the whole subtree and preserves the
  view restrictions the source inherited from ancestors outside it.
* *Duplicate* created the new page with no permissions at all, so duplicating a
  view-restricted page republished its content to anonymous visitors. The
  duplicate now carries the source's view restrictions, both its own and the
  ones it inherited.
* *Move* dropped the view restrictions that a page and its descendants
  inherited from the ancestors they left behind, exposing the pages themselves
  -- including descendants the moving user was not allowed to view -- to
  anonymous visitors. Moving now authorizes the whole subtree and materializes
  the inherited view restrictions on the moved page.

No action beyond upgrading is required. Pages that were copied, duplicated or
moved *before* the upgrade keep the permissions they were created with, so
review restricted branches for unrestricted copies made earlier.

The page wizard allowed creating pages below a parent on another site
---------------------------------------------------------------------

`GHSA-ppqv-h89f-6q9p <https://github.com/django-cms/django-cms/security/advisories/GHSA-ppqv-h89f-6q9p>`_:
in a multi-site installation, the *New page* and *New sub page* wizards accepted
an origin page from any site. The add permission was then checked against the
current site while the new page was attached to the foreign parent, so a staff
user with add rights on one site could insert pages into the page tree of a
site they have no rights on, leaving the new page with a parent on a different
site. The wizard now only resolves origin pages on the current site, and the
page creation form rejects a parent that belongs to another site -- for
superusers and with ``CMS_PERMISSION = False`` as well.

Adding a page from a page type disclosed restricted page types
--------------------------------------------------------------

`GHSA-7fqg-chmv-c89g <https://github.com/django-cms/django-cms/security/advisories/GHSA-7fqg-chmv-c89g>`_
(low severity): with ``CMS_PERMISSION = True``, the *Page type* field of the
add-page form narrowed the choices it rendered to the current site's page
types, but validated a submitted value against *every* page type in the
database. A staff user who may add a page could therefore submit the id of a
page type on another site, or one protected by a view restriction, and have its
placeholders, plugins and extensions copied into a page they own -- without the
view restrictions of the source.

Page types cannot be created through the interface in django CMS 4 and 5, so
only databases that still carry page types migrated from django CMS 3, or
created programmatically, are affected. The add-page form, the page wizard and
*Duplicate* now accept only page types of the current site, require view
permission on the source, and carry the source's view restrictions over to the
new page.

Stored XSS in the page delete confirmation escalated editors to administrators
------------------------------------------------------------------------------

`GHSA-mgv8-5r6j-2gjq <https://github.com/django-cms/django-cms/security/advisories/GHSA-mgv8-5r6j-2gjq>`_:
a staff user who may change a page could store markup in that page's url through
the *Overwrite URL* field -- a value containing no ``/`` bypassed url validation
entirely and was copied verbatim to ``PageUrl.path``. The page delete
confirmation screen marked the url safe when rendering it, so the stored markup
executed in the browser of whoever opened that screen, typically an
administrator about to delete the page. The script runs on the admin origin: it
cannot read the ``HttpOnly`` session cookie, but it can read the CSRF token and
issue authenticated requests as its victim, which turns an ordinary content
editor into an administrator.

``CMS_PERMISSION = True`` is not a mitigation -- it only limits which pages an
attacker can poison to the ones they may already edit. A second route stores the
payload on the home page, where ``ChangePageForm.clean()`` returned early and
never validated the value; it is ignored while the page is the home page and
becomes the live ``PageUrl.path`` as soon as another page takes that role.

Two changes fix this. The confirmation screen no longer marks the page url safe
and builds the page entry with ``format_html()``, and a path without a ``/`` is
now validated rather than skipped -- in the new
``ChangePageForm.clean_overwrite_url()``, so that the home page is covered too.

Upgrading is required even where every editor is trusted today: validation does
not clean values that are already stored, and paths written through ``cms.api``
or a direct model save never pass through the form at all. Only the output
encoding protects those rows. Audit the existing data with::

    from cms.models import PageUrl
    PageUrl.objects.filter(path__regex=r"[<>]")

**************************************
Backward incompatible changes in 5.1.3
**************************************

View restrictions follow pages that are copied, duplicated or moved
===================================================================

The security fixes above change how permissions behave around page copies and
moves:

* A page moved out of a restricted branch stays restricted at its new location.
  The view grants it inherited are written to the moved page as ``can_view``
  ``PagePermission`` rows (no other flag is carried over). To publish such a
  page, remove the restriction explicitly -- which requires the *can change
  permissions* right on it.
* ``Page.move_page()`` accepts a new optional ``user`` argument and now writes
  ``PagePermission`` rows. Pass the acting user so that the permission caches
  are invalidated for them::

      page.move_page(target, position, user=request.user)
* The move endpoint answers ``403`` when the moved subtree contains pages the
  user may not view and the destination would grant them access, mirroring the
  behaviour of copy.
* Two new methods support this: ``Page.get_view_restrictions()`` snapshots the
  ``can_view`` grants that protect a page, and ``Page.apply_view_restrictions()``
  recreates such a snapshot on a page at its new location. Code that relocates
  pages outside of ``Page.move_page()`` or ``Page.copy_with_descendants()``
  should use them.
* ``cms.utils.page_permissions`` gained ``user_can_relocate_descendants()`` with
  the thin wrappers ``user_can_copy_descendants()`` and
  ``user_can_move_descendants()`` for authorizing an operation against a whole
  subtree rather than its root.

See :doc:`/explanation/permissions` for the full picture of how permissions
behave when pages are moved, copied or deleted.

Page creation validates the page type and parent more strictly
================================================================

* ``AddPageForm.source`` only accepts page types below the current site's
  page-type root. Previously only the rendered choices were narrowed; the field
  now also narrows its queryset. Code that passes a page type from another site
  to the form, or to ``CreateCMSPageForm``, gets a validation error.
* ``AddPageForm`` gained ``clean_source()``, which requires view permission on
  the source, and its ``from_source()`` now applies the source's view
  restrictions to the new page. ``DuplicatePageForm`` inherits both instead of
  defining its own. The denial message is set per form through the new
  ``source_permission_denied`` class attribute.
* Submitting both ``cms_page`` (adding a translation) and ``source`` to
  ``AddPageForm`` is rejected: a translation reuses the existing page and would
  bypass the view restrictions applied in ``from_source()``.
* ``CreateCMSPageForm.clean_parent_page()`` rejects a parent on another site,
  and ``WizardStep1Form`` only accepts pages of the current site. Custom wizards
  that deliberately created pages across sites no longer work.

The current user is stored behind a wrapper
===========================================

To fix ``CurrentUserMiddleware`` hanging requests under ASGI, the
``cms.utils.permissions._current_user`` context variable no longer holds the
user itself but a private wrapper. Use the public helpers
``get_current_user()``, ``set_current_user()`` and ``reset_current_user()``
instead of accessing the context variable directly.

Page paths reject angle brackets
================================

The input validation above rejects values that earlier releases accepted:

* ``relative_url_regex`` no longer allows ``<`` and ``>`` anywhere in the value.
  It previously excluded them from the leading segment only, so markup passed as
  soon as one safe character preceded it (``foo/a<img src=x onerror=...>``).
* ``validate_url_uniqueness()`` now validates single-segment paths as well.
  Paths without a ``/`` used to skip validation entirely.
* Two helpers back this up in ``cms.forms.validators``: ``validate_path()``
  dispatches on whether the value contains a ``/``, and ``validate_path_segment()``
  checks a single segment against the new ``path_segment_regex``. Code that
  writes page paths outside the admin forms should call ``validate_path()``.

Paths already stored in the database are left untouched; only new input is
rejected. They are, however, escaped on output from now on.
