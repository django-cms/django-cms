####################
5.0.12 release notes
####################

*September 18, 2026*

Welcome to django CMS 5.0.12!

This is a patch release of the 5.0 series. It contains **six security fixes**
for broken access control in the page tree, the add-page form, the page wizard,
the move-plugin endpoint and the global page permission admin, which is why we
recommend that all users of django CMS 5.0.x upgrade as soon as possible. Read
the security fixes and their backward-incompatible effects before updating an
existing project. This release contains no migrations.

The same fixes are contained in django CMS 5.1.3.

If you are upgrading from django CMS 4.1 or earlier, read the release notes of
all versions in between, in particular the :ref:`5.0.0 release notes
<upgrade-to-5.0.0>`.

*******************************
Django and Python compatibility
*******************************

django CMS supports **Django 4.2, 5.0, 5.1, and 5.2**. We highly recommend and
only support the latest release of each series.

It supports **Python 3.9, 3.10, 3.11, 3.12, and 3.13**. As for Django we highly
recommend and only support the latest release of each series.

************************
How to upgrade to 5.0.12
************************

Before upgrading, back up your database and review the
:ref:`backward-incompatible changes <upgrade-5.0.12-backward-incompatible>`
below.

Update your project's ``requirements.txt`` file to require (at least) django CMS
5.0.12 and run ``pip install -r requirements.txt``.

If you are upgrading from an earlier version of django CMS, read the release
notes for all the versions between your current version and this one. Check
the :ref:`release notes <release-notes>` for each version to see if there are
any special instructions.

This release contains no migrations, but it does change static files, so
collect them again::

    python manage.py collectstatic --noinput
    python manage.py cms check

********************
What's new in 5.0.12
********************

Security fixes
==============

The same fixes are contained in django CMS 5.1.3. This release fixes six
advisories. All of them require an authenticated staff account; none is
exploitable anonymously. We recommend that all users upgrade as soon as
possible.

Page-tree copy, duplicate and move disclosed view-restricted pages
------------------------------------------------------------------

This release fixes broken access control in the page tree's *Copy*, *Duplicate*
and *Move* operations. All three require ``CMS_PERMISSION = True`` and at least
one per-page view restriction: an installation that does not use the permission
system has nothing to disclose, because ``Page.has_view_restrictions()`` is
always ``False`` there. Each of them needs a staff session that may add pages;
none is exploitable anonymously, but the content they expose is readable
anonymously afterwards.

`GHSA-976q-w6ch-6w82 <https://github.com/django-cms/django-cms/security/advisories/GHSA-976q-w6ch-6w82>`_
covers all three, which share a root cause, their prerequisites and their fix:

* *Copy* authorized only the root of the subtree it was asked to copy, while
  every descendant below it was copied and recreated without its view
  restrictions. A delegated editor who could view one public page therefore
  obtained a publicly readable copy of every view-restricted page below it.
  Selecting *Copy permissions* did not help: the flag was passed to the
  descendants but not to the copied root, so the root lost its own permission
  records as well. Copying now authorizes the whole subtree and preserves the
  view restrictions the source inherited from ancestors outside it.
* *Duplicate* created the new page with no permissions at all, so duplicating a
  view-restricted page republished its content to anonymous visitors. The
  duplicate now carries the source's view restrictions, both its own and the
  ones it inherited.
* *Move* dropped the view restrictions that a page and its descendants
  inherited from the ancestors they left behind, exposing the pages themselves
  -- including descendants the moving user was not allowed to view -- to
  anonymous visitors. Moving now authorizes the whole subtree and materializes
  the inherited view restrictions on the moved page.

No action beyond upgrading is required. Pages that were copied, duplicated or
moved *before* the upgrade keep the permissions they were created with, so
review restricted branches for unrestricted copies made earlier.

Adding a page authorized the parent from the query string
----------------------------------------------------------

`GHSA-g52p-phr3-hvx9 <https://github.com/django-cms/django-cms/security/advisories/GHSA-g52p-phr3-hvx9>`_:
with ``CMS_PERMISSION = True``, the add-page admin checked the add permission
against the parent named in the query string (``?parent_page=``), while the page
was created under the ``parent_page`` submitted in the form body -- which was
only checked to belong to the current site. A staff user whose page permissions
are confined to one part of the page tree could therefore create pages anywhere
in it, including at root level. ``AddPageForm.clean_parent_page()`` now re-checks
the permission against the parent the page is actually created under, and against
the site when no parent is submitted. The flaw allowed page *insertion* only: no
existing page could be read, changed or deleted through it.

The page wizard allowed creating pages below a parent on another site
---------------------------------------------------------------------

`GHSA-ppqv-h89f-6q9p <https://github.com/django-cms/django-cms/security/advisories/GHSA-ppqv-h89f-6q9p>`_:
in a multi-site installation, the *New page* and *New sub page* wizards accepted
an origin page from any site. The add permission was then checked against the
current site while the new page was attached to the foreign parent, so a staff
user with add rights on one site could insert pages into the page tree of a site
they have no rights on, leaving the new page with a parent on a different site.
The wizard now only resolves origin pages on the current site, and the page
creation form rejects a parent that belongs to another site -- for superusers and
with ``CMS_PERMISSION = False`` as well.

Adding a page from a page type disclosed restricted page types
--------------------------------------------------------------

`GHSA-7fqg-chmv-c89g <https://github.com/django-cms/django-cms/security/advisories/GHSA-7fqg-chmv-c89g>`_
(low severity): with ``CMS_PERMISSION = True``, the *Page type* field of the
add-page form narrowed the choices it rendered to the current site's page types,
but validated a submitted value against *every* page type in the database. A
staff user who may add a page could therefore submit the id of a page type on
another site, or one protected by a view restriction, and have its placeholders,
plugins and extensions copied into a page they own -- without the view
restrictions of the source.

Page types cannot be created through the interface in django CMS 4 and 5, so only
databases that still carry page types migrated from django CMS 3, or created
programmatically, are affected. The add-page form, the page wizard and
*Duplicate* now accept only page types of the current site, require view
permission on the source, and carry the source's view restrictions over to the
new page.

The move-plugin endpoint disclosed plugin content through ``plugin_parent``
---------------------------------------------------------------------------

`GHSA-79vf-xh44-8cpm <https://github.com/django-cms/django-cms/security/advisories/GHSA-79vf-xh44-8cpm>`_:
the *paste* and *cut* paths of the move-plugin endpoint resolved the
client-supplied ``plugin_parent`` without scoping it to the target placeholder.
Because the endpoint renders its response from the new plugin's parent, a staff
user with change permission on a single placeholder could name any plugin id and
have that plugin's rendered subtree returned -- including plugins on pages they
have no permission for, on other sites, and in other users' clipboards. The copy
was also created with a parent outside its own placeholder.

The parent is now looked up within the target placeholder and language on every
path, including the case where ``plugin_parent`` names the plugin's existing
parent. This flaw has been present since django CMS 3.0; unsupported release
lines will not receive a patch.

Delegated permission managers could grant themselves page rights
-----------------------------------------------------------------

`GHSA-cx9c-3cc5-gg94 <https://github.com/django-cms/django-cms/security/advisories/GHSA-cx9c-3cc5-gg94>`_:
with ``CMS_PERMISSION = True``, the *Page global permissions* admin offered every
``can_*`` flag regardless of the rights the acting user held. A non-superuser
whose only elevated right was ``can_change_permissions`` could therefore grant
themselves -- or anyone else -- ``can_publish``, ``can_delete``,
``can_change_advanced_settings`` and ``can_move_page``, site-wide. The per-page
permission inline had always restricted the offered flags; the global admin had
no equivalent check.

The admin now offers only the flags the manager holds, and refuses a grant of a
flag they do not hold on every selected site. Grants that carry flags beyond the
manager's rights, or that cover a site where they may not manage permissions, can
no longer be changed or deleted by them, so their user, group or sites cannot be
used to move those rights elsewhere. See the backward incompatible changes below.

Because ``GlobalPagePermission`` rows carry no audit fields, review the existing
rows after upgrading and check Django's admin log for entries created by
non-superusers.

***************************************
Backward incompatible changes in 5.0.12
***************************************

View restrictions follow pages that are copied, duplicated or moved
===================================================================

The security fixes above change how permissions behave around page copies and
moves:

* A page moved out of a restricted branch stays restricted at its new location.
  The view grants it inherited are written to the moved page as ``can_view``
  ``PagePermission`` rows (no other flag is carried over). To publish such a
  page, remove the restriction explicitly -- which requires the *can change
  permissions* right on it.
* ``Page.move_page()`` accepts a new optional ``user`` argument and now writes
  ``PagePermission`` rows. Pass the acting user so that the permission caches
  are invalidated for them::

      page.move_page(target, position, user=request.user)
* The move endpoint answers ``403`` when the moved subtree contains pages the
  user may not view and the destination would grant them access, mirroring the
  behaviour of copy.
* Two new methods support this: ``Page.get_view_restrictions()`` snapshots the
  ``can_view`` grants that protect a page, and ``Page.apply_view_restrictions()``
  recreates such a snapshot on a page at its new location. Code that relocates
  pages outside of ``Page.move_page()`` or ``Page.copy_with_descendants()``
  should use them.
* ``cms.utils.page_permissions`` gained ``user_can_relocate_descendants()`` with
  the thin wrappers ``user_can_copy_descendants()`` and
  ``user_can_move_descendants()`` for authorizing an operation against a whole
  subtree rather than its root.

See :doc:`/explanation/permissions` for the full picture of how permissions
behave when pages are moved, copied or deleted.

Page creation validates the page type and parent more strictly
===============================================================

* ``AddPageForm.clean_parent_page()`` requires add permission on the submitted
  parent (``user_can_add_subpage()``), or on the site when no parent is
  submitted (``user_can_add_page()``). Code that posts a ``parent_page``
  differing from the ``?parent_page=`` query parameter, or that instantiates the
  form for a user without add rights on that parent, gets a validation error.
  Adding a translation (``cms_page``) is exempt.
* ``AddPageForm.source`` only accepts page types below the current site's
  page-type root. Previously only the rendered choices were narrowed; the field
  now also narrows its queryset. Code that passes a page type from another site
  to the form, or to ``CreateCMSPageForm``, gets a validation error.
* ``AddPageForm`` gained ``clean_source()``, which requires view permission on
  the source, and its ``from_source()`` now applies the source's view
  restrictions to the new page. ``DuplicatePageForm`` inherits both instead of
  defining its own. The denial message is set per form through the new
  ``source_permission_denied`` class attribute.
* Submitting both ``cms_page`` (adding a translation) and ``source`` to
  ``AddPageForm`` is rejected: a translation reuses the existing page and would
  bypass the view restrictions applied in ``from_source()``.
* ``CreateCMSPageForm.clean_parent_page()`` rejects a parent on another site, and
  ``WizardStep1Form`` only accepts pages of the current site. Custom wizards that
  deliberately created pages across sites no longer work.

Global page permissions are limited to the rights of the manager
=================================================================

The fix for GHSA-cx9c-3cc5-gg94 restricts what a non-superuser can do in the
*Page global permissions* admin. Superusers and installations with
``CMS_PERMISSION = False`` are unaffected.

* A ``can_*`` flag can only be granted by a manager who holds it on *every* site
  the grant covers. A grant with no sites selected covers all sites and requires
  an equally unrestricted grant of the flag.
* The manager must hold ``can_change_permissions`` on every site the grant
  covers. Managing permissions on one site no longer reaches grants for another.
* A flag counts only together with the Django permissions its page action
  requires -- ``can_publish``, for instance, needs ``cms.change_page`` and
  ``cms.publish_page``. ``can_view`` has no Django counterpart.
* Grants outside those limits are no longer editable or deletable by that
  manager: the change and delete views answer ``403``.
* ``cms.utils.permissions`` gained ``get_grantable_global_permissions(user,
  site_ids=None)``, the single source of truth for what a user may hand out.
  Projects with their own permission admin should use it.

Existing ``GlobalPagePermission`` rows are not changed by the upgrade. A row that
was created through the old admin keeps its flags; only what managers may grant
from now on is restricted.
